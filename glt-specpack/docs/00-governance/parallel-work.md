# Параллельная работа

Как делится работа между исполнителями — людьми и AI-агентами одинаково.

Правило: **задачи делятся по bounded context, не по фичам.** Один контекст — один исполнитель на отрезке времени. Фича, проходящая через два контекста, режется по границе события; контракт события согласуется до старта обоих исполнителей.

---

## Контексты и владельцы

| Контекст | Ответственность | Владелец | Класс фактов |
|---|---|---|---|
| **Registry** | ID, aliases, ActionSpec, policy refs | registry | `glt-id-registry` |
| **Compilation** | компилятор снимков, валидация схем | snapshot-compiler | `intended-topology` |
| **Collection** | git и CI collectors, materialized-факты | git-collector | `materialized-build` |
| **Evaluation** | state evaluator, freshness, конфликты | telemetry-collector | `observed-runtime` |
| **Impact** | change и incident propagation | engineering | `impact-propagation-rules` |
| **Execution** | planner, policy, runner, audit | policy-engine | `policy-approval`, `audit-chain` |
| **Presentation** | dashboard, CLI, слой глифов | engineering | — (проекция) |
| **Trust** | bootstrap, witness, authority | external-t0 | `bootstrap-trust` |

Владелец — роль из [`../../trust/authority-map.yaml`](../../trust/authority-map.yaml), а не человек. Один класс фактов — один владелец; это то же правило, что защищает snapshot от переписывания дашбордом. Ровно один владелец на контекст: контекст с двумя владельцами не имеет границы, по которой можно разделить работу.

Разделение **Collection** и **Evaluation** принято в 0.4.0. До этого они были единым контекстом Observation с двумя владельцами, и он давал цикл `Compilation ↔ Observation`: коллекторы подают факты в компилятор, а state evaluator потребляет снимок. Обоснование и граф — [`../PDA/03-domain-graph.md`](../PDA/03-domain-graph.md).

## Потоки данных на границах

Для каждой пары смежных контекстов названо событие, по которому проходит разрез. Источник имён — [`../../contracts/events/event-registry.yaml`](../../contracts/events/event-registry.yaml).

Это **потоки данных**, а не зависимости. Направление зависимостей — в графе контекстов; там, например, ребра `Execution → Trust` нет, хотя audit-записи текут именно туда.

| Граница | Событие | С шага |
|---|---|---|
| Registry → Compilation | `glt.snapshot.compiled` | DEV-08 |
| Collection → Compilation | `glt.snapshot.compiled` | DEV-13 |
| Compilation → Impact | `glt.impact.computed` | DEV-10 |
| Compilation → Evaluation | `glt.gate.evaluated` | DEV-15 |
| Impact → Execution | `glt.plan.created` | DEV-29 |
| Execution → Trust | `glt.audit.appended` | DEV-24 |
| Trust → внешний мир | `glt.witness.anchored` | DEV-28 |
| Impact → Presentation | — | проекция, не событие |
| Evaluation → Presentation | — | проекция, не событие |

Presentation читает и не публикует. Границы с ним не режутся событием: дашборд и CLI — производные проекции, а не контексты-источники (S-5).

До DEV-08 событий нет вообще. На волне 1 разрез между контекстами держится только на импортах (S-2), и это единственный механизм развязки.

Contexts `Collection` и `Evaluation` активируются на разных волнах: Collection с DEV-13, Evaluation с DEV-15. До волны 2 оба пусты, и разделение существует только как граница в графе.

## Общее ядро — зона архитектора

Изменения идут отдельными PR и **не выполняются агентами параллельно**:

- `glt-specpack/contracts/schemas/` — wire-контракты
- `glt-specpack/contracts/propagation/` — матрица распространения
- `glt-specpack/contracts/events/` — реестр событий
- `glt-specpack/registry/` и `glt-specpack/trust/`
- `control-plane/packages/domain` — канонизатор, digest, обход
- `control-plane/packages/contracts` — генерируемые типы

Причина простая: два исполнителя, одновременно правящие канонизатор, дают два ответа на PROTO-03, и оба будут зелёными в своих тестах.

## Протокол расширения графа

Расширение графа домена, новый тип связи, новая строка матрицы, новое событие, новая capability — **решение архитектора**.

Исполнитель, упёршийся в это, останавливается и формулирует запрос. Он не достраивает домен самостоятельно. Полный список стоп-условий — в [`AGENTS.md`](../../../AGENTS.md), раздел «Конфликт».

Запрос содержит: что требуется добавить, какую неопределённость это закрывает, какие инварианты затрагивает, почему существующих средств не хватает.

---

## Узкое место

В методологии v1.1 роли архитектора, доменного эксперта и техлида описаны как разные. **В этом проекте все три совмещены в одном человеке.**

Это нормально при одном исполнителе и деградирует при масштабировании: каждое расширение графа ждёт одного человека, и добавление исполнителей увеличивает очередь, а не скорость.

Измеряется метрикой `glt_graph_change_lead_time` ([`../OBSERVABILITY/metrics.md`](../OBSERVABILITY/metrics.md)) — время от запроса исполнителя до решения. Если растёт, то либо часть решений делегируется, либо часть контекстов замораживается по составу событий на период спринта.

Это метрика организации, а не кода. Она не имеет отношения к качеству реализации и не должна попадать на дашборд устойчивости продукта.

## Антипаттерны

| Антипаттерн | Почему ломает |
|---|---|
| Два исполнителя на одном контексте | Граница контекста была единственным механизмом развязки; без неё конфликт переносится в код и обнаруживается на merge. |
| Инвариант живёт в спеке, а не в тестах | Целостность держится на памяти архитектора. Работает при одном исполнителе, отказывает при двух. Это S-7. |
| `AGENTS.md` вместо проверок | Инструкция снижает частоту нарушений, но не гарантирует их отсутствие. Без CI это договорённость. |
| Архитектор как единственная точка сцепки | Пока все решения о домене идут через одного человека, исполнители встают в очередь. |
| Ревью только через CI | CI ловит нарушения известных инвариантов. Новый класс расхождения он не видит: его сначала должен заметить человек и превратить в правило. |
| Имя события придумано на месте | Реестр перестаёт быть источником правды в момент появления первого литерала мимо него. |

## Текущее состояние

Волна 1 идёт **одним исполнителем**. При таком режиме разделы про деление по контекстам и про узкое место не активны, а S-1, S-2, S-3, S-6, S-7 и S-10 всё равно включаются сразу: они дешевле в момент, когда кода нет, чем в момент, когда расхождение уже закрепилось.
