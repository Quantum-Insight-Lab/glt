# bootstrap-trust-fail

**Инвариант:** sheet INV-10 (верификатор использует T0-ключ вне проверяемого манифеста).
**Метрика:** `bootstrap_verify_pass` на чистой установке.

Верификатор не смог подтвердить bootstrap-манифест при старте. Control plane не поднимается: доверие терминируется на T0, и без него всё остальное недоказуемо.

## Detect

- `glt verify` завершается до валидации схем.
- Подпись манифеста не проверяется ключом из `trust/seed-public-keys/`.
- Ключ, указанный в метаданных манифеста, отсутствует в seed-каталоге.
- Тест INV-10: манифест, подписанный только встроенным в него ключом, прошёл проверку — это отказ механизма, а не отказ подписи.

## Mitigate

1. **Определить, чего именно не хватило.** Отсутствие ключа, несовпадение подписи и порядок загрузки — три разных отказа.
2. **Проверить порядок загрузки.** Ключи читаются из seed-каталога **до** разбора манифеста. Если верификатор сначала парсит манифест, чтобы узнать, какой ключ брать, и берёт его оттуда же — это нарушение INV-10, и проверка не имеет смысла независимо от результата.
3. **Ключ dev-only?** `glt-dev-only-2026` — рабочий ключ с опубликованной приватной половиной. Он проходит проверку в CI и обязан отвергаться как release trust root по [`release-policy.yaml`](../../../trust/release-policy.yaml). Отказ при попытке релиза с ним — правильное поведение, а не инцидент.
4. **Ротация.** Если ключ был заменён без grace period, старые манифесты перестают проверяться. Ротация добавляет новый ключ, держит оба, затем деприкейтит старый.
5. **Не подписывать манифест заново, чтобы «пройти».** Подпись, поставленная для обхода отказа, снимает единственную защиту от подмены артефакта.

## Escalate

Control plane не запускается — это не деградация, а отказ старта. Read-only режим тоже недоступен: снимки, которые он отдавал бы, не подтверждены.

Если приватный ключ утрачен, нужен новый T0 с новой release identity и переподписание манифеста; предыдущие релизы остаются подтверждёнными старым ключом, пока он в `allowed`.

## Postmortem

- Какой из трёх отказов: ключ, подпись или порядок загрузки.
- Проверялся ли порядок загрузки тестом, а не обзором.
- Не был ли dev-only ключ единственным на момент попытки релиза.
- Описана ли процедура ротации настолько, чтобы её выполнить без этого runbook.
